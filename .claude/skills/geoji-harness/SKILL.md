# geoji-harness

계획서(`docs/plans/`)의 카드 하나 또는 절 하나를 코드로 만드는 순서다. 명세를 대조하고 구현한 뒤 둘로 나눠 검증한다.

혼자 다 하지 않는 이유는 셋이다. 명세 대조와 구현을 한 눈이 하면 계획서에 없는 값을 자기도 모르게 채운다. 구현한 눈이 검증하면 자기가 만든 것을 옳다고 읽는다. 코드 검토와 테스트 검증은 서로 독립이라 같이 돌리면 시간이 들지 않는다.

geoji-web 하네스와 다른 점. 설계 단계가 없다. 계획서 §3이 파일 경로와 시그니처를 이미 정해 두었으므로 명세 대조가 그 표를 옮기는 것으로 설계를 대신한다. 디자인 검토도 없다. 대신 계획서 §4.2의 테스트 케이스가 실제 테스트 파일과 맞는지 보는 검증이 있다.

## 쓰는 도구

`Agent`와 `SendMessage`다. 에이전트 정의는 `.claude/agents/`에 있고 `subagent_type`에 파일 이름을 확장자 없이 넣는다.

| subagent_type          | 하는 일                                          | 산출                                     |
| ---------------------- | ------------------------------------------------ | ---------------------------------------- |
| `geoji-spec-auditor`   | 계획서에서 무엇을 어디에 만들지 확인, 미결정 판정 | `_workspace/01_spec.md`                  |
| `geoji-implementer`    | 코드와 테스트 작성                               | 소스·테스트 파일, `_workspace/02_impl.md` |
| `geoji-code-reviewer`  | 의존 방향, 계약, enum, 중복, 프롬프트 위치        | `_workspace/03_code_review.md`           |
| `geoji-test-verifier`  | §4.2 케이스와 테스트 파일 대조, 게이트 실행       | `_workspace/03_test.md`                  |

호출은 이렇게 한다. `model`은 넷 모두 `opus`다.

```
Agent({
  subagent_type: "geoji-spec-auditor",
  name: "spec",
  model: "opus",
  description: "명세 대조",
  prompt: "..."
})
```

`_workspace/`는 `.gitignore`에 있어 커밋되지 않는다. 중간 산출물을 남겨 두면 후속 요청에서 처음부터 다시 하지 않아도 된다.

일이 끝난 에이전트는 `SendMessage`로 `shutdown_request`를 보내 정리한다. 에이전트 정의의 `tools`에 `SendMessage`가 없으면 그 에이전트는 응답하지 못해 세션이 남는다. 도구를 좁힐 때 이것을 빼지 않는다.

## 게이트

```bash
uv run ruff check .
uv run ruff format --check .
uv run pytest -q
```

셋 다 통과해야 완료다. `pyproject.toml`이 아직 없으면(작업 1 §3.1 전) 게이트도 없다. 그 요청 자체가 게이트를 만드는 일이니 골격을 만든 뒤 위 셋이 도는지부터 확인한다.

## Phase 0. 어디서 시작할지 정한다

`_workspace/`를 보고 실행 모드를 고른다.

| 상태                           | 모드        | 시작 지점                                           |
| ------------------------------ | ----------- | --------------------------------------------------- |
| `_workspace/` 없음             | 초기        | Phase 1                                             |
| 있고 같은 대상을 고치라는 요청 | 부분 재실행 | 고칠 단계부터. 뒤 단계는 다시 돈다                  |
| 있고 다른 대상 요청            | 새 실행     | `_workspace/`를 `_workspace_prev/`로 옮기고 Phase 1 |

그리고 규모를 판정한다. 작은 일에 넷을 부르면 기다리는 시간이 만드는 시간보다 길어진다.

| 규모 | 무엇                                   | 부르는 에이전트                                         |
| ---- | -------------------------------------- | ------------------------------------------------------- |
| 작음 | 카드 하나(S). 파일 한두 개             | implementer, test-verifier. 명세 대조는 직접 한다       |
| 보통 | 카드 여럿 또는 §3 절 하나              | 넷 전부. 구현은 1명                                     |
| 큼   | 작업 하나(계획서 한 장) 전체            | 넷 전부. 구현은 파일을 나눠 최대 3명                    |

규모를 정했으면 사용자에게 한 줄로 알린다. 무엇을 만들고 누구를 부르는지.

## Phase 1. 명세를 대조한다

`geoji-spec-auditor` 1명. 요청 원문과 짐작되는 문서·카드를 넘긴다.

```
prompt: |
  요청: {사용자 원문}
  짐작되는 문서·카드: {01 CT-03, 05 §3.4 또는 "모르겠음"}

  docs/plans/의 해당 문서 §2·§3·§4와 10-backend-contract.md, 00-INDEX.md §8.4에서
  대상을 확정하고 _workspace/01_spec.md에 정의된 형식으로 쓴다.
  미결정에 걸리는 것이 있으면 blocked 절에 남기고 임시 기본값을 제안하지 않는다.
```

## 게이트 A. 미결정이면 멈추고 묻는다

`_workspace/01_spec.md`의 `blocked`가 비어 있지 않으면 **여기서 멈춘다.** `AskUserQuestion`으로 묻고 답을 받은 뒤에 진행한다.

이 저장소는 계획서에 없는 값을 코드에 박기 전에 묻기로 되어 있다. 협의 중인 값에 그럴듯한 기본값을 채우면 그것이 사실상 확정이 된다.

자주 걸리는 것. `00 §8.4`의 `- [ ]` 항목(D-23, 검수관 모델), `10 §14`의 백엔드 채택 대기 항목, 실측 뒤 채울 빈칸(`____초`), 백엔드가 아직 만들지 않은 API(`10 §15.1` 실태). 작업 3부터는 백엔드 API가 거의 반드시 걸리므로 가짜 백엔드(`tests/fakes/`)로 진행할지를 선택지에 넣는다.

질문에는 선택지를 함께 낸다. 무엇이 왜 막혔고 각 선택이 무엇을 바꾸는지 적는다.

## 게이트 B. 승인이 필요하면 묻는다

`_workspace/01_spec.md`의 `approval`이 비어 있지 않으면 멈추고 묻는다. `pyproject.toml` 의존성 추가, `contracts/*.schema.json` 변경(`schema_version`이 오른다), 새 마이그레이션 번호, ports 시그니처 변경, 계획서 §3 표에 없는 파일 신설이 여기 해당한다.

`approval`이 비어 있으면 사용자를 부르지 않고 Phase 2로 간다.

## Phase 2. 구현한다

`geoji-implementer`. 테스트도 구현 몫이다. §4.2에 적힌 테스트 파일을 소스와 함께 쓴다. 규모가 큼이면 파일 목록을 겹치지 않게 나눠 최대 3명까지 한 메시지에서 동시에 부른다. 같은 파일을 둘에게 주지 않는다.

```
prompt: |
  _workspace/01_spec.md를 읽고 구현한다.
  네 몫: {파일 목록. 소스와 테스트}
  다른 담당이 맡은 파일: {목록}. 건드리지 않는다.
  게이트 A·B에서 정해진 것: {사용자 답변, 없으면 "없음"}
  _workspace/02_impl.md에 보고를 쓴다. 여럿이면 02_impl_{n}.md에 쓴다.
```

## Phase 3. 둘로 나눠 검증한다

`geoji-code-reviewer`와 `geoji-test-verifier`를 **한 메시지에서 동시에** 부른다. 하나는 코드를 읽고 하나는 계획서와 테스트를 대조하고 게이트를 돌린다. 서로 보는 것이 달라 순서가 필요 없다.

```
prompt: |
  방금 구현한 것을 검토한다. _workspace/의 02_impl*.md 전부에 목록이 있다.
  이번에 쓴 보고서: {실제 파일 목록}
  자기 담당 파일에 정해진 형식으로 쓴다.
```

## Phase 4. 고치고 보고한다

두 보고서를 읽고 오케스트레이터가 직접 고친다. 고치는 에이전트를 또 부르지 않는다.

1. 같은 줄이나 같은 원인을 가리키는 지적을 하나로 합친다
2. 심각도 높음부터 고친다
3. 고치지 않는 것은 이유를 적는다. 계획서와 다른 동작이 되거나 이번 범위 밖이면 넘긴다
4. 게이트를 다시 돌린다. 통과할 때까지 고친다
5. 같은 게이트가 세 번 반복 실패하면 더 시도하지 않는다. 변경을 되돌리고 명세로 돌아간다

보고는 이렇게 한다.

```markdown
## 만든 것

| 경로 | 무엇 | 계획서 |

## 검증

| 관점   | 판정 | 남은 것 |
| 코드   |      |         |
| 테스트 |      |         |

## 고친 것

## 넘긴 것

반영하지 않은 것과 이유.

## 확인하지 못한 것

실제 벤더·DB 없이 fake로만 본 것, 미결정이라 비워 둔 값.

## 계획서에 반영할 것

완료된 카드(CT-NN), 구현하며 발견한 계획서와의 어긋남. 반영은 사용자가 시킬 때 plans-format 룰대로.
```

커밋하지 않는다. 계획서 카드 체크도 직접 하지 않는다. 사용자가 시킬 때만 한다.

마지막에 한 줄로 묻는다. 고칠 곳이 있는지, 워크플로우에서 바꾸고 싶은 것이 있는지.

## 에러

| 무슨 일                          | 어떻게                                                                                        |
| -------------------------------- | --------------------------------------------------------------------------------------------- |
| 에이전트가 빈 결과나 실패를 반환 | 같은 프롬프트로 한 번만 다시 부른다. 또 실패하면 그 단계 없이 진행하고 보고서에 누락을 적는다 |
| 산출 파일이 없음                 | 다음 단계를 시작하지 않는다. 앞 단계를 다시 부른다                                            |
| 검토 지적이 서로 어긋남          | 지우지 않는다. 양쪽을 보고서에 함께 적고 어느 쪽을 따랐는지 밝힌다                            |
| 게이트 3회 반복 실패             | 되돌리고 명세로 돌아간다. 네 번째를 시도하지 않는다                                           |
| 테스트가 실제 벤더를 부르려 함   | 키를 넣어 통과시키지 않는다. fake provider로 바꾸거나 `tests/evaluations/`로 옮긴다           |

## 테스트 시나리오

**정상.** "01 §3.5 domain 모듈 만들어줘"가 들어온다. Phase 0이 보통 규모로 판정한다. spec-auditor가 `intensity`, `lexicon`, `attack_angles`, `validation` 네 파일과 §4.2의 `tests/unit/test_{intensity,lexicon,attack_angles,validation}.py`를 옮기고 `blocked` 없음, `approval` 없음으로 적는다. implementer가 넷과 테스트를 쓴다. code-reviewer가 실측 스크립트에서 복사된 대문자 `MILD`를 잡고, test-verifier가 §4.2 `test_lexicon`의 `ID_IN_TEXT` 케이스가 빠진 것을 잡는다. 둘 다 고치고 게이트를 통과시킨 뒤 보고한다.

**게이트 A.** "03 백엔드 클라이언트 만들어줘"가 들어온다. spec-auditor가 `10 §15.1`에서 백엔드에 5 API가 아직 없음을 확인하고 `blocked`에 넣는다. 오케스트레이터가 멈추고 묻는다. 가짜 백엔드(`tests/fakes/backend_app.py`)를 먼저 만들어 그 위에서 진행할지, 백엔드 회신을 기다릴지. 답을 받기 전에 계약을 임의로 정하지 않는다.
