# 백엔드 전달 사항 기록

백엔드 담당은 이 저장소의 코드를 읽지 않는다. 백엔드가 읽는 문서는 두 종류다(9/20 정리).

- **10(`docs/plans/10-backend-contract.md`)** — 상시 계약. 인증·헤더·거부 본문(§4.7), `ai.jobs` INSERT 규약(§3), 내부 API 모양(§4), finalize(§5), 배포·연동(§16). "지금 코드가 하는 대로"만 적고 `(원문)`·`(제안)`·날짜별 정정 문장은 두지 않는다
- **날짜별 전달 문서(19, 20, …)** — 새 기능 하나가 백엔드에 요구하는 것. `§0 할 일 체크리스트` → 계약 절들 → `수용 검사` → `미결`. 첫 문서는 19(데모 AI 배심원). 9/19 까지의 전달 원문은 `archive/10-backend-contract-2026-09-19.md`

## 언제 적는가

코드나 계획서를 바꾼 결과가 아래 하나에 해당하면 **같은 커밋에서** 문서를 고친다.

- 백엔드가 할 일이 생김(새 엔드포인트·잡 종류·환경변수·복사 파일·계정) → **그 기능의 전달 문서**에 §0 체크리스트 한 줄 + 계약 절. 진행 중인 전달 문서가 없으면 다음 번호로 새로 만든다
- 상시 계약이 바뀜(헤더·거부 코드·INSERT 표 값·finalize 검증·배포 키) → 10 의 해당 절을 코드 사실로 고친다. 전달 문서에서 10 의 절을 가리킬 때는 `10 §4.7` 처럼 번호로
- 백엔드 회신이 필요한 것이 생기거나 답이 옴 → 그 전달 문서의 미결 표. 답이 오면 행을 확정으로 바꾸고 본문도 고친다
- AI 이미지 태그·`prompt_bundle_version` 대조값 → 그 태그를 전달한 문서. 10 §16.3 은 절차만

## 어떻게 적는가

- 전달 문서 §0 은 `| # | 할 일 | 절 | 상태 |`. 상태는 `미전달` → `전달 9/NN` → `반영`. 상태를 바꾸는 것은 사용자다. 에이전트는 `미전달` 로만 추가한다
- 10 의 §번호는 인용 ID 라 바꾸지 않는다. 새 절은 `§4.8`·`§16.4` 처럼 붙인다. 전달 문서는 절 번호를 자유롭게 매기되 다른 문서가 `19 §5` 처럼 인용하므로 한 번 쓴 번호를 밀지 않는다
- 키 목록은 `.env.example`, 기본값은 README 가 정본이다. 문서에는 "직접 적어야 하는 것" 과 없을 때 무슨 일이 나는지만
- 비밀값의 실제 값은 적지 않는다. 키 이름과 전달 경로만
- 전달 문서가 전부 `반영` 이 되면 사용자가 `archive/` 로 옮기고 10 §0.1 전달 문서 목록의 상태를 `반영` 으로 바꾼다
- orca 워커는 스펙 Ownership 이 `docs/**` 를 막는다. 그때는 `_workspace/04_report.md` 에 `## 백엔드 전달` 절을 두고 §0 형식의 줄과 고칠 절을 적는다. 문서로 옮기는 것은 머지 뒤 코디네이터 또는 사용자가 한다

## 하지 않는 것

- 같은 계약을 두 문서에 복제하지 않는다. 상시 규약은 10 에 있고 전달 문서는 `10 §n` 으로 가리킨다
- 10 에 날짜별 할 일·미결을 다시 쌓지 않는다. 그것은 전달 문서 몫이다
- AI 파트 내부 결정(프롬프트, 모델 선택, 예산)은 전달 문서에 적지 않는다. 백엔드가 할 일이 없는 것은 우리 쪽 명세(18 등)에만
