# 백엔드 전달 사항 기록

백엔드 담당은 이 저장소의 코드를 읽지 않는다. 백엔드가 읽는 문서는 **10(`docs/plans/10-backend-contract.md`) 한 장**이다(9/14 통일, 별도 전달 파일 없음). 우리가 만든 것 중 백엔드가 알아야 붙일 수 있는 것은 전부 10 에 적는다. 계약은 §1~§12, 할 일과 전달 상태는 §0.1, 회신 대기는 §14, 배포·연동은 §16 이다.

## 언제 적는가

코드나 계획서를 바꾼 결과가 아래 하나에 해당하면 **같은 커밋에서** 10 을 고친다.

- 배포 환경변수가 생기거나 필수가 되거나 값이 정해짐 → §16.1
- 백엔드가 부르거나 healthcheck 에 쓸 엔드포인트가 생기거나 응답이 바뀜 → §16.2(내부 API 동작이면 §4 도)
- 백엔드 저장소로 복사해 가거나 실행할 파일이 생기거나 바뀜 → §16.3. `templates-v1.json`, 마이그레이션 `004` 초안, 무효화·reaper SQL, compose 조각, 이미지 태그
- 계약의 모양·enum·상한·필수 필드가 바뀌거나 10 과 코드의 어긋남을 발견함 → 해당 절 본문
- 백엔드 회신이 필요한 것이 생기거나 답이 옴 → §14. 답이 오면 행을 확정으로 바꾸고(`plans-format` 룰 결정 절차 2) 본문도 고친다

위 어느 경우든 백엔드가 할 일이 생기면 §0.1 체크리스트에 한 줄을 더한다.

## 어떻게 적는가

- 본문은 계약 문장 자체를 코드 사실로 고친다. 고친 곳은 `(M/D 코드 대조)` 표시, 크게 바뀐 옛 문장은 `(원문)` 으로 남긴다. 기존 §번호는 바꾸지 않고 새 절은 `§4.7`·`§16.4` 처럼 붙인다
- §0.1 은 `| 날짜 | 무엇이 바뀌었나 → 백엔드가 할 일 | 절 | 상태 |`. 날짜는 `9/11` 식, 절은 10 안의 절(`§4.1`), 상태는 `미전달` → `전달 9/NN` → `반영`
- 새 줄은 §0.1 표의 **맨 위**에 넣는다. 위가 최신
- 키 목록은 `.env.example`, 기본값은 README 가 정본이다. 10 에는 "직접 적어야 하는 것" 과 없을 때 무슨 일이 나는지만
- 비밀값의 실제 값은 적지 않는다. 키 이름과 전달 경로만
- 상태를 `전달`·`반영` 으로 바꾸는 것은 사용자가 한다. 에이전트는 `미전달` 로만 추가한다
- orca 워커는 스펙 Ownership 이 `docs/**` 를 막는다. 그때는 `_workspace/04_report.md` 에 `## 백엔드 전달` 절을 두고 §0.1 형식의 줄과 고칠 10 절을 적는다. 10 으로 옮기는 것은 머지 뒤 코디네이터 또는 사용자가 한다

## 하지 않는 것

- 10 밖에 백엔드용 문서를 새로 만들지 않는다
- 같은 계약을 두 절에 복제하지 않는다. 한 절에 쓰고 다른 절은 `§n` 으로 가리킨다
- AI 파트 내부 결정(프롬프트, 모델 선택, 예산)은 §0.1 에 적지 않는다. 백엔드가 할 일이 없는 것은 §15.3 참고 표까지만
